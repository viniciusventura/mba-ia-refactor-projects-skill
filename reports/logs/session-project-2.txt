  Findings

  F-01 [CRITICAL] Credenciais hardcoded (AP-02)

  File: src/utils.js:2-6
  Principle: OWASP A07 / 12-Factor App (Config)
  Description: há 2 segredos escritos como texto fixo no código, sem leitura de
  ambiente: dbPass (linha 3) e paymentGatewayKey, com prefixo pk_live_ (linha
  4). Também há configuração fixa: dbUser (linha 2), smtpUser (linha 5) e port
  (linha 6). Nenhum arquivo do projeto usa process.env. A chave do gateway
  também vaza em log (ver F-03).
  Evidence:
  dbPass: "senha_super_secreta_prod_123",
  paymentGatewayKey: "pk_live_1234567890abcdef",
  Impact: quem tem acesso ao repositório tem a chave de produção do gateway e a
  senha do banco. Trocar um segredo exige novo deploy de código.
  Recommendation: extrair para src/config/index.js, lendo process.env
  (PAYMENT_GATEWAY_KEY, PORT, ADMIN_TOKEN), com um .env.example sem valores
  reais. Remover dbUser, dbPass e smtpUser, que nunca são usados (PT-02).
  Contract change: NO

  F-02 [CRITICAL] Armazenamento inseguro de senha (AP-03)

  File: src/utils.js:17-23, src/AppManager.js:18, 68-69
  Principle: OWASP A02 Cryptographic Failures
  Description: o "hash" badCrypto só repete os 2 primeiros caracteres do base64
  da senha, então o resultado depende apenas dos ~12 primeiros bits dela. Quando
  a senha não é enviada, ela vira o default "123456" (linha 68). O usuário do
  seed é gravado em texto puro ('123', linha 18). O projeto não usa bcrypt,
  scrypt, argon2 nem pbkdf2.
  Evidence:
  hash += Buffer.from(pwd).toString('base64').substring(0, 2);
  let hash = badCrypto(p || "123456");
  Teste executado: senhaforte, senha e se123 geram o mesmo valor c2c2c2c2c2. 123
  e 1234567 geram MTMTMTMTMT.
  Impact: as colisões são triviais e a reversão é imediata. Se o banco vazar,
  todas as senhas ficam expostas.
  Recommendation: usar o crypto.scrypt nativo do Node com salt aleatório por
  senha (sem dependência nova). O seed também passa a gravar hash, e a senha
  vira obrigatória na criação de usuário (PT-03).
  Contract change: YES: POST /api/checkout sem pwd para um e-mail novo passa a
  responder 400 "Bad Request" (hoje cria o usuário com a senha "123456"). Para
  e-mail já existente, pwd continua opcional.

  F-03 [CRITICAL] Exposição de dados sensíveis (AP-04)

  File: src/AppManager.js:45
  Principle: OWASP A01/A09
  Description: a cada checkout, o número completo do cartão e a chave de
  produção do gateway são escritos em log (1 ocorrência).
  Evidence:
  console.log(`Processando cartão ${cc} na chave ${config.paymentGatewayKey}`);
  Impact: o número do cartão e a chave do gateway ficam gravados nos logs, o que
  viola o PCI-DSS. Qualquer pessoa com acesso aos logs pode usá-los.
  Recommendation: remover o log. Se for necessário, registrar só os 4 últimos
  dígitos, sem a chave (PT-04 + PT-02).
  Contract change: NO

  F-04 [CRITICAL] Endpoint sensível sem autenticação (AP-05)

  File: src/AppManager.js:80, 131
  Principle: OWASP A01 Broken Access Control
  Description: duas rotas sensíveis estão abertas, e o projeto não tem nenhum
  mecanismo de autenticação (nem auth, nem jwt, nem middleware antes das rotas).
  GET /api/admin/financial-report expõe o faturamento e os nomes dos alunos.
  DELETE /api/users/:id apaga qualquer usuário.
  Evidence:
  app.get('/api/admin/financial-report', (req, res) => {
  app.delete('/api/users/:id', (req, res) => {
  Impact: qualquer cliente anônimo lê dados financeiros e pessoais ou apaga
  usuários. É explorável sem autenticação.
  Recommendation: criar o middleware requireAdmin em src/middlewares/auth.js,
  exigindo Authorization: Bearer <ADMIN_TOKEN>. O token vem do ambiente e é
  comparado em tempo constante. Sem token configurado, a rota fica fechada
  (PT-05).
  Contract change: YES: as duas rotas passam a responder 401 sem credencial
  válida. Com credencial, respondem o status original.

  F-05 [CRITICAL] God Class / God File (AP-06)

  File: src/AppManager.js:1-141, src/utils.js:1-25
  Principle: SRP (SOLID) + MVC
  Description: AppManager acumula responsabilidades de camadas diferentes:

  - rotas/HTTP (28, 80, 131)

  controllers/, routes/, services/ e middlewares/ (PT-06).

  F-06 [HIGH] Regra de negócio na camada errada (AP-07)

  File: src/AppManager.js:43-75, 46, 66-75, 89-127, 108-110
  Principle: SRP (SOLID) + MVC
  Description: há 3 regras de domínio dentro de handlers HTTP:
  - a aprovação do pagamento (cc.startsWith("4"), linha 46);
  - o fluxo "cria o usuário se não existe → matricula → paga → audita" (43-75);
  - o cálculo do faturamento por curso, que soma só os pagamentos PAID
    (108-110).
    Evidence:

  if (payment && payment.status === 'PAID') { courseData.revenue +=
  payment.amount; }
  Impact: a regra não pode ser reaproveitada (CLI, fila) nem testada sem HTTP. A

  Recommendation: a aprovação do pagamento vai para services/paymentService.js.
  A orquestração do checkout vai para controllers/checkoutController.js. O
  relatório é montado no controller, com os dados vindos do model (PT-07).
  Contract change: NO

  F-07 [HIGH] Estado global mutável / acoplamento sem DI (AP-08)

  File: src/utils.js:9, 14, 25; src/AppManager.js:7, 26
  Principle: DIP (SOLID)
  Description: globalCache é um objeto de módulo exportado e alterado a cada
  checkout (linha 14). Ele não tem limite de tamanho e nunca é lido. A conexão é
  criada dentro do construtor (new sqlite3.Database(':memory:')), sem injeção,
  e as rotas dependem de this/self capturados por closure.
  Evidence:
  let globalCache = {};
  function logAndCache(key, data) { globalCache[key] = data; }
  Impact: a memória cresce sem limite (uma chave por usuário) e o estado é
  compartilhado entre requisições. Também não dá para trocar o banco nos testes.
  Recommendation: remover o cache, que é escrito e nunca lido. A conexão passa a
  ser criada em database/connection.js e injetada nos models e controllers pelo
  composition root app.js (PT-08).
  Contract change: NO

  F-08 [HIGH] Operação multi-etapa sem transação: checkout (AP-09)

  File: src/AppManager.js:50-63, 69-71
  Principle: Integridade (ACID)
  Description: o checkout grava em até 4 tabelas (users 69, enrollments 50,
  payments 54, audit_logs 57) em callbacks aninhados, sem BEGIN/COMMIT/ROLLBACK.
  Evidence:
  this.db.run("INSERT INTO enrollments ...", [userId, cid], function(err) {
      self.db.run("INSERT INTO payments ...", [enrId, course.price, status],
  function(err) {
  Impact: se o INSERT do pagamento falhar, a matrícula fica gravada sem
  pagamento, e o aluno tem acesso ao curso sem pagar. Quando o pagamento é
  recusado, o usuário já foi criado.
  Recommendation: criar helpers promisificados e um transaction() em
  database/connection.js. A criação do usuário, a matrícula, o pagamento e a
  auditoria passam a rodar numa única transação, com async/await (PT-09).
  Contract change: NO

  F-09 [HIGH] Exclusão física de usuário com histórico (AP-09)

  File: src/AppManager.js:131-137
  Principle: Integridade (ACID)
  Description: DELETE FROM users apaga o aluno e deixa enrollments e payments
  órfãos, como a própria resposta admite. Depois disso, o relatório financeiro
  mostra 'Unknown' no lugar do aluno.
  Evidence:

      res.send("Usuário deletado, mas as matrículas e pagamentos ficaram sujos

  órfãos.
  Recommendation: soft delete (PT-09):

    DATETIME;
  - o DELETE vira um UPDATE;
  - as leituras de negócio (busca de usuário por e-mail no checkout) filtram
    deleted = 0;
  - o relatório financeiro continua mostrando o aluno.

  Contract change: YES: o texto da resposta muda de "Usuário deletado, mas as
  matrículas e pagamentos ficaram sujos no banco." para "Usuário removido." (o

  de 'Unknown'.

  Description: o relatório roda 1 query de cursos, mais 1 de matrículas por

      this.db.all("SELECT * FROM enrollments WHERE course_id = ?", [c.id], ...
          enrollments.forEach(enr => { this.db.get("SELECT name, email FROM 
  users WHERE id = ?", ...
  Impact: o tempo de resposta cresce linearmente com o número de matrículas.
  Recommendation: usar uma única query com LEFT JOIN courses → enrollments →
  users → payments, agrupada no controller (PT-10).
  Contract change: NO. Hoje, a ordem dos alunos dentro de cada curso depende da
  ordem de chegada dos callbacks. Depois da mudança, ela passa a seguir o id da
  matrícula.

  F-11 [MEDIUM] Código duplicado (AP-11)

  F-12 [MEDIUM] Erro engolido / sem handler central / validação ausente (AP-12)
