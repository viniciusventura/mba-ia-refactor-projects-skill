  Refactoring Plan (Phase 3 preview)

  Strategy: B) evolução incremental. Ficam models/, routes/ (camada View,
  equivalente a views/), os Blueprints e as URLs.

  Target structure:
  - Novos: config/settings.py, controllers/ (task, user, category, report,
    health, validators), middlewares/error_handler.py e middlewares/auth.py.
  - Novas rotas: routes/category_routes.py e routes/health_routes.py.
  - Utilitários: utils/constants.py e utils/time.py.
  - App: app.py vira só create_app(). from app import app, db continua
    funcionando para o seed.
  - Removidos: utils/helpers.py e services/ (ambos código morto), e
    marshmallow/requests do requirements.

  Contract changes requiring approval:
  - F-03: a chave password sai de GET /users/<id>, POST /users, PUT /users/<id>
    e do user de POST /login.
  - F-04: o token passa a ser assinado e vai no header Authorization: Bearer.
    Sem token válido a resposta é 401; sem o papel ou a propriedade exigidos, é
    403:
    - Só admin: DELETE /users/<id>, POST|PUT|DELETE /categories.
    - Admin, manager ou dono da task: PUT|DELETE /tasks/<id>.
    - Qualquer usuário autenticado: POST /tasks e GET /users/<id>.
    - O próprio usuário ou admin: PUT /users/<id>. Os campos role e active só
      podem ser alterados por admin.
    - POST /users: continua público, mas role diferente de user exige admin.
  - F-06: GET /users, GET /users/<id>/tasks, GET /reports/summary e GET 
    /reports/user/<id> passam a exigir token.
  - F-08:
    - Os DELETE viram soft delete, com deleted_at e deleted_by em tasks, users e
      categories.
    - A migração é um ALTER TABLE ADD COLUMN idempotente.
    - DELETE /users/<id> não apaga mais as tasks do usuário.
    - Registro removido responde 404 nas leituras por id.
  - F-11: as entradas inválidas que hoje dão 500 passam a dar 400.
